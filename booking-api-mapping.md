# Booking API Mapping

For connecting the website to Booking. Base URL: `http://localhost:5001`.
This matches the Booking code; integration with teammate services still needs testing.

## 1. Search rooms

```http
GET /api/rooms?check_in=2026-11-15&check_out=2026-11-17&room_type=double
```

Room types: `single`, `double`, `king_suite`. Availability manages three rooms of each type. Send exactly these three search parameters, with no request body.

Response (200):

```json
{"rooms": [{"room_id": "R101", "room_number": "101", "room_type": "double", "capacity": 2}]}
```

No matches returns `{"rooms": []}`. Searching does not reserve a room.

## 2. Create a booking

```http
POST /api/bookings
Content-Type: application/json
Idempotency-Key: <UUID>
```

Generate the key with `crypto.randomUUID()`. Reuse the same key and details when retrying the same attempt; use a new key for a different attempt.

Send exactly:

```json
{
  "guest_name": "Alex Tan",
  "room_id": "R101",
  "check_in": "2026-11-15",
  "check_out": "2026-11-17",
  "guest_count": 2
}
```

Confirmed response (201; example ID):

```json
{
  "booking_id": "B001",
  "guest_name": "Alex Tan",
  "room_id": "R101",
  "check_in": "2026-11-15",
  "check_out": "2026-11-17",
  "guest_count": 2,
  "status": "confirmed",
  "notification_status": "sent",
  "created_at": "2026-11-15T08:00:00Z",
  "updated_at": "2026-11-15T08:00:00Z"
}
```

Save `booking_id` for viewing/cancelling. Actual IDs are generated by Booking.

## 3. View a booking

`GET /api/bookings/{booking_id}`

No body. Returns 200 with the full Booking object above, including its current status.

## 4. Cancel a booking

`POST /api/bookings/{booking_id}/cancel`

No body. Returns the full Booking object: 200 with `status: "cancelled"`, or 202 with `status: "cancelling"` while room release is unresolved. Only confirmed bookings can begin cancellation. Cancelling an already cancelled booking returns 200 unchanged.

## How the website handles responses

| HTTP result | What to do |
| --- | --- |
| 200 / 201 | Display the returned data. For orders, read `status`; a successful GET may also return pending or rejected orders |
| 202 | Read `status`: pending means booking is processing; cancelling means cancellation is processing |
| 400 | Show `error.message` so the guest can correct the input |
| 404 | Show `error.message`: room or booking not found |
| 409 | Show `error.message`: room unavailable, request conflict or cancellation not allowed |
| Other errors / network failure | Show a temporary-error message; preserve the booking ID and request key |

Errors have this shape; booking_id is included when an associated order exists:

```json
{"error": {"code": "ROOM_UNAVAILABLE", "message": "Room unavailable for these dates."}, "booking_id": "B001"}
```

The UI can show `error.message` as plain text without separate logic for every error code. Always send JSON for creation; non-JSON returns 415.

## Important notes

- Names must not be blank; use real YYYY-MM-DD dates with check-out after check-in. Creation needs a positive integer guest_count; Availability checks capacity.
- For pending/cancelling orders, call View every two seconds for up to 30 seconds, then offer manual refresh. A timeout does not prove failure. If a create reply is lost, retry with the original key and details.
- Repeated create requests return the original order's current status or saved rejection, without creating another order.
- Notification failures do not undo a confirmed booking. notification_status may stay pending while Booking retries; the UI does not call Notification.
- The frontend can keep booking IDs in its session. Booking uses booking_id, not the guest name or session, to retrieve orders. No login or ownership check is implemented.
- Serve the website at `http://localhost:3000`. For another origin, set Booking's WEBSITE_ORIGIN to that exact origin and restart Booking.

The website calls only Booking. Booking calls Availability to search/reserve/check/release, and Notification to record confirmations. Internal endpoints, exact error codes and backend rules are in [api-guide.md](api-guide.md). No internal API key is required by this Booking version.
